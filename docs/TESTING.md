# Testing Policy

This document defines the testing policy for GoMetadata. All contributors and
automated agents must follow these rules without exception.

---

## 1. The Core Rule: Failures Are Bugs

**A test that fails is a bug in the library, never a bug in the test.**

When a test assertion fails, fix the library. Do not suppress the failure with
`t.Skip`, `t.Log`, or a weakened assertion. Removing or weakening a test to make
the build green is forbidden.

---

## 2. `t.Skip` Usage

`t.Skip` is permitted only for **external resource absence or OS-level capability
limitations**. It is forbidden in all other circumstances.

### 2.1 Permitted uses

A `t.Skip` call is valid if and only if it falls into one of these three categories:

**a) Corpus file absent** — the test exercises a real-world image file from the
optional corpus (`testdata/corpus/`). The corpus is not checked into git and may
not be present in CI or a fresh checkout. The skip must be conditional on a
`os.IsNotExist` / file-not-found check and must direct the user to the download
command.

```go
// Correct: conditional on actual file absence.
if _, err := os.Stat(path); os.IsNotExist(err) {
    t.Skipf("corpus file absent (run testdata/download.sh): %s", path)
}
```

**b) OS/privilege limitation** — the test requires a capability that is not
universally available: running as root suppresses permission checks; `os.Symlink`
may be unsupported; timezone data may be absent. The skip must be conditional on
a runtime check that proves the limitation.

```go
// Correct: conditional on a runtime capability check.
if err := os.Chmod(dir, 0o555); err != nil {
    t.Skipf("cannot chmod dir (running as root or unsupported OS): %v", err)
}
```

**c) Self-protection for boundary/capacity constants** — a test that verifies a
size cap does not block legitimate traffic may skip if the test fixture itself
exceeds the cap. This means the test constant must be updated, not that the test
should disappear.

```go
// Correct: guard against stale test constants.
if len(raw) >= maxXMPDocumentBytes {
    t.Skip("fixture unexpectedly large; update the test constant")
}
```

### 2.2 Forbidden uses

`t.Skip` must **never** be used to:

- Hide a parser or writer bug ("GPS() returned ok=false; GPS data may not be
  accessible via EXIF" — this is a bug; fix the parser).
- Suppress an assertion on a **synthetic** fixture. If the test builds the fixture
  itself, the fixture must always satisfy the assertion; any mismatch is a test
  helper bug, not a skip condition.
- Gate a test on a condition that is always true in a well-functioning library
  (e.g., "IPTC or XMP nil after reading synthetic JPEG").
- Silence a nil-pointer guard that exists because the caller forgot to handle
  errors from `Read` or `ReadFile`.

In all of these cases, use `t.Fatal` or `t.Fatalf` so the failure is visible.

### 2.3 Message requirements

Every `t.Skip` call must:

1. Identify the specific condition that triggered it ("corpus file absent",
   "running as root").
2. Tell the reader how to make the test run ("run testdata/download.sh").
3. Never use the word "skipping" without explaining why — "skipping" alone is not
   a reason.

## 3. Fixture Strategy

### 3.1 Committed fixtures (`testdata/fixtures/`)

Critical test paths that must execute in every CI run — including Example tests
and integration tests that prove top-level API correctness — must use fixtures
committed to the repository at `testdata/fixtures/`.

**What belongs in `testdata/fixtures/`:**
- Synthetic JPEG/TIFF files generated from known binary layouts. These are small
  (typically < 20 KB) and are generated by the `TestMain` function in
  `testmain_test.go` if absent.
- Real-world files that are small enough to commit (< 10 KB), contain no
  personally identifiable information, and are needed for specific tag or format
  coverage that cannot be synthesised (e.g., the BigTIFF reference files).

**What does NOT belong in `testdata/fixtures/`:**
- Large real-world camera files (> 10 KB). These go in `testdata/corpus/` and
  are guarded with a corpus skip (see §2.1a).
- Any file containing personally identifiable information (GPS coordinates of a
  private address, personal names in IPTC fields, etc.).

### 3.2 TestMain fixture generation (`testmain_test.go`)

The root package's `TestMain` function automatically generates synthetic fixtures
before any test or Example function runs. Fixture generation:

- Is idempotent: if the fixture file already exists it is not regenerated.
- Uses hand-crafted binary TIFF/JPEG payloads when the public API cannot express
  the required tag value (e.g., ColorSpace, WhiteBalance, GPS altitude).
- Must pass `go test -run TestMain` in isolation.

When adding a new Example function that requires a specific metadata value, either:
- Reuse an existing fixture if it carries the needed tag; or
- Add a new fixture spec to `generateFixtures()` in `testmain_test.go`.

### 3.3 Optional corpus (`testdata/corpus/`)

Large real-world images are stored in `testdata/corpus/` and are excluded from
git via `.gitignore`. They are downloaded via `testdata/download.sh` (or
`make testdata`).

Corpus tests must all be guarded with conditional `t.Skip` calls as described in
§2.1a. They provide extra coverage when the corpus is available but their absence
must not block a CI run.

---

## 4. Example Functions

Go Example functions (functions named `ExampleXxx`) produce documentation and
are run as tests. Their `// Output:` comment must exactly match the printed
output. Additional requirements:

- Example functions must use fixtures from `testdata/fixtures/`, never from
  `testdata/corpus/`. The corpus is not present in CI.
- The `// Output:` value must be stable across machines and Go versions. Do not
  include absolute file sizes, timestamps, or other values that vary by platform.
  If the example only needs to prove a write succeeds, print `output written: true`
  rather than a byte count.
- If the correct output depends on a tag value computed from a synthetic fixture,
  the `testmain_test.go` fixture generator must be updated at the same time as the
  example.

---

## 5. Race Detector

All tests must be race-safe. Run with `-race` before any merge:

```sh
go test -race ./...
```

Tests that use `testing.AllocsPerRun` must not call `t.Parallel()` — the alloc
counter is not safe across goroutines. Add `//nolint:paralleltest` on the test
function when this restriction applies.

---

## 6. Fuzz Tests

Every component that processes untrusted binary input must have a `FuzzXxx`
function. Fuzz targets must not call `t.Skip` under any condition; they receive
random bytes and must never panic or data-race regardless of the input.

---

## 7. Conformance Tests

The normative conformance batteries in `docs/conformance/` define the
compliance contract. Every rule ID (e.g., `S-08`, `JPEG-04`, `ROB-03`) maps
directly to a sub-test name. These tests must never be skipped — they are the
proof of specification compliance.

If a conformance sub-test fails in CI, it is a regression in the library. Fix the
library; do not change the test to pass.

---

## 8. Summary Table

| Situation | Correct action |
|---|---|
| Parser returns unexpected nil on synthetic input | `t.Fatal` — fix the parser |
| Test helper builds a fixture that lacks an expected tag | `t.Fatal` — fix the helper |
| `GPS()` returns `ok=false` on GPS-tagged file | `t.Fatal` — fix the decoder |
| Corpus file not present on disk | `t.Skipf` with download instructions |
| Running as root, permission check not enforced | `t.Skipf` with explanation |
| `os.Symlink` not supported on this OS | `t.Skipf` with explanation |
| Timezone data not available | `t.Skipf` with explanation |
| Fixture byte count exceeds a safety cap constant | `t.Skipf` — update the constant |
