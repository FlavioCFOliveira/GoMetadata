# Changelog

All notable changes to GoMetadata are documented in this file.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Versions are listed in descending order (newest first). GoMetadata adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- **`exif.TagNameIn`, `exif.TagContext`, `exif.EXIF.MakerNoteContext`** (`exif/tag_context.go`, `exif/makernote_tags_gen.go`, #395, #397): `TagNameIn(ctx, id)` names a tag in the IFD that `ctx` names (IFD0, Exif, GPS, Interoperability, IFD1) or in the MakerNote of one of 16 manufacturer tables (Canon, Casio Type 1 and 2, Fujifilm, Kyocera, Leica, Nikon Type 1 and Type 2/3, Olympus, Panasonic, Pentax, Ricoh, Sanyo, Sigma, Sony, Sony Ericsson; 643 tags). `TagNameIn(ContextInterop, 1)` is `InteropIndex` and `TagNameIn(ContextGPS, 1)` is `GPSLatitudeRef`; `TagName` is unchanged. `EXIF.MakerNoteContext` gives the context of a parsed file. The tables are generated by `internal/tools/mngen` from metadata-extractor (tag IDs and names only); no table exists for Apple, DJI, Samsung and Leica Type 5 (the source takes their tag reference from the ExifTool documentation) or for the binary Kodak and Reconyx layouts. `BenchmarkTagNameIn` 1.6 to 7.5 ns/op, 0 allocations.
- **`exif.EXIF.MakerNoteLens`** (`exif/makernote_lens.go`, #396): the lens recorded in the MakerNote: the Canon LensModel tag (0x0095) and the Nikon lens specification (tag 0x0084, for example `18-55mm f/3.5-5.6`).

- **`Segment`, `SegmentEXIF`, `SegmentIPTC`, `SegmentXMP`, `Metadata.MarkModified`** (`metadata.go`, `write_plan.go`, #387): `MarkModified` records that the exported field `EXIF`, `IPTC` or `XMP` was edited directly, so that `Write` encodes that segment. It is serialised like the `Set*` methods. A marked segment that is nil is left as the image has it; `MarkModified` does not remove a segment. See the package documentation, section "Writing".
- **`jpeg.InjectKeeping`, `jpeg.Keep`** (`format/jpeg/jpeg.go`, #387): `Inject` for a write that changes only some segments; the segments in the `Keep` (`KeepEXIF`, `KeepIPTC`, `KeepXMP`) stay as the source has them, byte for byte and in the same place. A kept EXIF whose MakerNote addresses data outside the EXIF stream (Olympus, `exif.ExternalOffsets`) is written from the payload given, with the offsets set for the new layout.
- **`png.InjectKeeping`, `png.Keep`** (`format/png/png.go`, #405): the PNG equivalent; the chunks of the kept segments are copied as they are, CRC included. `Inject` is unchanged: a nil payload removes the chunk.
- **`exif.EXIF.GPSAltitude` and `exif.EXIF.GPSTimeStamp`** (`exif/exif.go`, `exif/gps.go`, #385): the GPS altitude in metres (negative below sea level) and the UTC hour, minute and second of the GPS fix. `Metadata.Altitude` uses `GPSAltitude`.
- **`exif.IFDEntry.Strings`** (`exif/ifd.go`, #386): the NUL-separated strings of a multi-string ASCII or UTF-8 value (TIFF 6.0 §2, p. 15). Trailing NUL bytes are not separators; an empty string between two separators keeps its position.
- **`exif.EXIF.Make` and `exif.EXIF.Software`** (`exif/exif.go`, #401): the IFD0 Make and Software text, ended at the first NUL byte, with trailing white space removed.
- **`jpeg.ErrTooManySegments`, `png.ErrNoImageHeader`** (`format/jpeg/errors.go`, `format/png/errors.go`, #403): `jpeg.Inject` returns `ErrTooManySegments` for a source with more than 65536 separate runs of metadata segments to replace, and writes nothing; `png.Inject` returns `ErrNoImageHeader` when it has EXIF or XMP to add and the file has no IHDR chunk before IEND or the end of the file.

- **`tiff.InjectWithMagic`** (`format/tiff/inject_stream.go`, #392): `Inject` for a TIFF-based container whose header carries a magic other than `0x002A` (Olympus ORF, Panasonic RW2) and for a source that is not held in memory; `orf.Inject` and `rw2.Inject` write through it. It reads the metadata prefix of the source, streams the image data from it, and refuses a source (or an output) beyond the 4 GiB that classic TIFF offsets address with `tiff.ErrFileTooLarge`. `tiff.Inject` is unchanged.

- **`tiff.ExtractCompact`, `tiff.Sparse`** (`format/tiff/sparse.go`, #389): `ExtractCompact` is `Extract` for a classic TIFF or DNG whose IFDs lie far from each other; it returns the compacted metadata — the IFD directories, their out-of-line values and the JPEG thumbnails, side by side, with the offsets that `exif.Parse` follows rewritten — instead of the prefix of the file that reaches the last IFD. `Sparse.Restore` writes the offsets of the file back after the parse.

### Changed

- **`Metadata.LensModel` falls back to the MakerNote** (`metadata.go`, #396): when the EXIF tag 0xA434 and the XMP lens are absent, it returns `EXIF.MakerNoteLens`. A file that had a lens model returns the same one. On the test corpus 101 files that returned an empty string now return the lens, equal to the ExifTool value (Nikon:Lens, Canon:LensModel). Canon lens identifiers without a LensModel tag, and Sony ones, are not translated: the available name tables derive from ExifTool.
- **A HEIF/AVIF write streams the file** (`format/heif/stream.go`, `heif.Inject`, `Write`, #390): the top-level box headers are read through a small window, the meta box, the moov boxes whose chunk offsets move and the new payloads are built in memory, and every other byte is copied from the source to the destination through a pooled buffer. `IMG_2928.HEIC` (6.2 MB) allocated 6.2 MB per write and now allocates 31 KB, in 129 us instead of 548 us; `IMG_2929.HEIC` (2.7 MB) 2.8 MB to 31 KB. The bytes written are unchanged (51 corpus files, 9 writes each, identical SHA-256). `heif.Inject` has no limit on the size of the file any more (it was 256 MiB): `heif.ErrFileTooLarge` is returned only for a meta or moov box above 256 MiB. The source must be seekable: an `io.ReadSeeker` whose `Seek` fails now returns an error; before, it was read whole. A source that ends before the size it reported ends the write with an error after part of the output has been written; every error that follows from the structures is still returned before the first byte.
- **A WebP write streams the file** (`format/webp/webp.go`, `webp.Inject`, `Write`, #391): two passes over the chunk headers compute the RIFF size and the VP8X chunk, and the image chunks are copied from the source. `webpvp8x.webp` (1.6 MB) allocated 1.9 MB per write and now allocates 3.4 KB, in 31 us instead of 140 us. The bytes written are unchanged (33 corpus files, 9 writes each). There is no limit on the size of the file (it was 256 MiB); `webp.ErrFileTooLarge` now means an output beyond the 4 GiB of the 32-bit RIFF size field, and is returned before anything is written. The source must be seekable.
- **An ORF or RW2 `Inject` streams the file** (`format/raw/orf/orf.go`, `format/raw/rw2/rw2.go`, #392): `orf.Inject` and `rw2.Inject` read the 4 magic bytes and the metadata prefix and stream the image data; `Write` of these containers already did (#291, #293) and is unchanged. `orf.Inject` of the 24 MB `Olympus TG-4.orf` allocated 50 MB per call and now allocates 3.1 MB (the prefix, 1.55 MB, and the header built from it, as large). The bytes written are unchanged (36 ORF and 19 RW2 corpus files). The 256 MiB limit on the file is gone for a seekable source; a source that cannot report its size is still read whole, up to 256 MiB, and a source of 4 GiB or more is refused with `ErrFileTooLarge`.
- **A JPEG write copies the bytes after EOI instead of holding them** (`format/jpeg/trailer.go`, `internal/trailer/source.go`, `jpeg.Inject`, `Write`, #393): the AFCP, FotoStation and Samsung trailer finders search the area after the image for their signatures with a streaming scan and read only the bytes they inspect; the rest, the audio file of a Samsung trailer for example, is copied from the source. `samsung-s9.jpg` (8.5 MB, 4.6 MB trailer) allocated 4.6 MB per write and now allocates less than 30 KB. The same trailers are found and rewritten (1701 corpus files, 10 writes each, identical SHA-256).
- **`Read` of a JPEG with Extended XMP allocates less** (`format/jpeg/extacc.go`, `xmp/`, #394): the chunks of one extended packet are assembled into one block per GUID, sized from the declared length and capped by the bytes left in the file, so chunks that arrive in order need no merge copy and the wire frame is built in reserved headroom; the XML element table is sized from the tag count of the document; and `Encode` no longer regrows or clones a large output. `exiv2-bug922.jpg` allocated 23.0 MB per `Read` and now allocates 6.8 MB; `Google Cardboard.jpg` 36.2 MB and now 11.7 MB. The parsed XMP and the bytes `Write` produces are unchanged.
- **`Read` of a TIFF or DNG whose IFDs follow the image data reads only the metadata** (`read.go`, `write.go`, `format/tiff/sparse.go`, #389): the Pentax QS1 DNG of the test corpus (22.6 MB, Exif IFD at the end of the file) allocated 22.7 MB per `Read` and now allocates 0.2 MB; 15 of the 75 TIFF-family corpus files above 4 MiB are read this way. The parsed metadata and the bytes `Write` produces are unchanged. `Metadata.RawEXIF` of such a file returns the leading bytes of the file (a prefix that does not reach every IFD) instead of the prefix up to the last IFD; `Write` reads the metadata prefix of the source again, as before. A file whose compacted metadata cannot be proved equal to the whole file (overlapping ranges, a parse warning, a MakerNote away from the header, BigTIFF) is read as before.
- **Changed (behaviour notice): results and write output differ from 1.5.0.** Code that relies on the former behaviour must be updated.
  - **`Write` encodes only the modified segments** (`write.go`, `write_plan.go`, `metadata.go`, #387): the `Set*` methods mark the segments they change, and every other segment is copied from the source. A direct edit of `m.EXIF`, `m.IPTC` or `m.XMP` is no longer written unless the segment is marked with `MarkModified`. Exceptions: a segment that `Metadata` holds and the image does not (for example an EXIF assigned after reading an image with none) is written without a mark; when the image written is not the image `m` was read from, every segment of `m` is written, as before. In TIFF, DNG, CR2, NEF, ARW, ORF and RW2 the EXIF IFDs are laid out again from `m.EXIF` in every write that is not a plain copy of the source, so a direct EXIF edit is written when another segment is; direct IPTC and XMP edits still need the mark.
  - **A `Read` followed by a `Write` with no change returns the source byte for byte** (`write_plan.go`, #387), in every container, with the default `PreserveUnknownSegments(true)`. In JPEG and PNG an unmodified segment keeps its bytes and its place; a JPEG IPTC segment that is not modified is not rewritten, so its IPTC digest is left as the source has it. In TIFF-based containers a write that changes anything is not byte-identical: the IFDs and the data after them move; metadata and image data are preserved.
  - **Damaged JPEG and PNG sources are now written** (`format/jpeg/splice.go`, `format/png/png.go`, #403): a JPEG whose segments cannot be followed before the first scan header (no marker prefix, a length below 2, a segment past the end of the file, a cut header) is copied from the first unreadable byte, with the metadata added before it; before, the write failed. After IHDR, a PNG chunk that cannot be followed (header cut short, length past the end of the file) is copied with the rest of the file, and no IEND is added after it. In the test corpus, 206 JPEG and PNG files that a write refused are now written (entries removed from `testdata/corpus_write_rejects.txt`).
  - **A PNG without IHDR now returns an error** (`format/png/png.go`, #403): `Write` and `png.Inject` return `png.ErrNoImageHeader` when EXIF or XMP is to be added to a file with no IHDR chunk; before, the metadata was silently not written.
  - **Text values end at the first NUL byte** (`exif/ifd.go`, `iptc/encoding.go`, `exif/makernote_parse.go`, #386): `exif.IFDEntry.String` returns the bytes before the first NUL (it removed trailing NUL bytes only, and returned the bytes after an inner NUL), and the decoded text of every IPTC dataset ends at the first NUL. MakerNote detection reads Make the same way. The stored bytes do not change.
  - **Trailing white space is removed from Make, Model, Software, Artist and LensModel** (`exif/exif.go`, `exif/ifd.go`, `metadata.go`, #386, #401): `Metadata.Make`, `CameraModel`, `Software`, `LensModel` and `Creator`, and the matching `exif.EXIF` accessors, return the tag text without trailing space, tab, line feed, vertical tab, form feed or carriage return, as ExifTool does (`Exif.pm` `s/\s+$//`). `Caption` and `Copyright` are not trimmed, and the stored bytes do not change. A Make, Model, Software or LensModel of only white space counts as absent, so the XMP value is used. `Creator` returns the first creator of the trimmed Artist string. A value set with trailing white space (`SetMake("x  ")`) is read back without it; the XMP mirror of a `Set*` call receives the value as given.
  - **GPS values: SRATIONAL is read, a zero denominator is absent** (`exif/gps.go`, #385, #402): `GPS`, `GPSAltitude` and `GPSTimeStamp` accept GPSLatitude, GPSLongitude, GPSAltitude and GPSTimeStamp written as SRATIONAL instead of RATIONAL (a manufacturer deviation from Exif 3.1 §4.6.6, for example HMD Nokia 8.3 5G) when the numerator is not negative and the denominator is positive; before, such a value was reported as absent. A value with a zero denominator, RATIONAL or SRATIONAL, or a negative SRATIONAL, is reported as absent (ok=false), and `Parse` adds a warning naming the tag; before, a zero denominator in a coordinate gave a wrong latitude or longitude.
- **A JPEG write replaces a metadata segment in place** (`format/jpeg/splice.go`, #403): a new segment takes the place of the first old segment of its kind, and the other old segments of that kind are dropped. Only the segment headers before the first scan header are read; every other byte is copied as it is, including what follows EOI. The Olympus preview offsets follow the new layout.
- **A PNG write replaces the old eXIf and XMP chunks in place** (`format/png/png.go`, #403): a new chunk takes the place of the first old chunk of its kind; only a kind the file has none of goes after IHDR. The bytes after IEND are copied. A file that ends at a chunk boundary without IEND still receives one.

### Fixed

- **A JPEG write keeps the JFIF APP0 segment first** (`format/jpeg/splice.go`, #400, #403): `Write` and `jpeg.Inject` wrote new metadata segments right after SOI, before the JFIF APP0 segment (ITU-T T.871 §6.3). A segment of a kind the source has none of now goes after JFIF, the JFXX extension segments and a leading Adobe APP14, in the order EXIF, XMP, IPTC.
- **A PNG write keeps the chunks of unmodified segments** (`write.go`, `format/png/png.go`, #405): `Write` after `SetKeywords` or `SetISO` removed the unmodified eXIf or XMP chunk, because `png.Inject` reads a nil payload as "remove". This corrects a defect of #387 that no release contains. The other containers were audited and were not affected.
- **README: IPTC in RAW files** (`README.md`, #388): the format table listed IPTC as unsupported in CR2, NEF, ARW, DNG, ORF and RW2; it is read and written there (IFD0 tag `0x83BB`). `readme_iptc_raw_test.go` checks the table against the code.

## [1.5.0] - 2026-10-17

### Added

- **`exif.EncodeRebased`** (`exif/makernote_rebase.go`, `exif/makernote_walk.go`, #317, #318): encodes an EXIF like `Encode` and repairs the MakerNote for the position the stream gives it: the offsets of a layout that counts from the TIFF header are set for the new position (Canon's footer follows), and the data that the MakerNote IFD addresses outside its declared bytes (Olympus C-720UZ values, the Nikon `PreviewIFD`/`NikonScanIFD` and the preview image, Olympus and Ricoh sub-IFDs) is carried. `Write` uses it for JPEG, PNG, WebP and HEIF/AVIF. `Encode` is unchanged: the TIFF-family writers still place the MakerNote and rebase it themselves. See `docs/conformance/exif-tiff.md` R-20 to R-26.
- **`exif.New`, `EXIF.CompressedPrimary`, `(*EXIF).NeedsImageSize`** (`exif/mandatory.go`, #321): `New(compressedPrimary)` returns an EXIF with the tags that Exif 3.1 marks mandatory (Tables 17-19); `CompressedPrimary` (set by `Read` for a JPEG) tells the setters which column of the support-level tables applies to the IFDs they create; `NeedsImageSize` reports an Exif IFD created for a JPEG that still lacks PixelXDimension and PixelYDimension, which `Write` fills from the JPEG frame header. See S-46 and S-47.
- **`jpeg.ImageSize` and `jpeg.ErrNoFrameHeader`** (`format/jpeg/size.go`, #321): the pixel dimensions of the first frame header of a JPEG, reading only the segment headers.
- **`exif.TypeIFD`, `exif.IFD.Sub`, `exif.SubIFDs`** (`exif/type.go`, `exif/ifd.go`, #320, #319): `TypeIFD` is code 13, the TIFF IFD type; `IFD.Sub` holds the Exif and GPS IFDs (and the Interoperability IFD) that an IFD of the chain after IFD0, the thumbnail IFD, addresses itself (Exif 3.1 Table 21).
- **Exif 3.1 tags in the registry** (`exif/tag_extended.go`, `exif/tag.go`, #320): `LearningOptOutIn` (`0x9287`), `DevelopmentType`, `DevelopmentTypeDescription`, `DistortionCorrection`, `ChromaticAberrationCorrection`, `ShadingCorrection`, `NoiseReduction` (`0xA40D`-`0xA412`), and the constants `TagExifVersion`, `TagComponentsConfiguration`.
- **MakerNote layouts: "SONY MOBILE", every "SANYO" version, "JVC "** (`exif/makernote_detect.go`, #317): the Xperia, Sanyo 2.1 and JVC notes are recognised (ExifTool `MakerNotes.pm`), so `Parse` reads their IFD and a write repairs them. A headerless little-endian Nikon note (E990, E5000, Coolpix 775) is recognised for the repair only; `Parse` still reads no IFD from it.
- **`cr3.ErrNoMetadataContainer`** (`format/raw/cr3/errors.go`, #347): returned by `cr3.Inject` (and so by `Write`) when a requested EXIF or XMP payload cannot be stored because the file has no `moov` box (it then also matches `cr3.ErrNoMoovBox`) or, for EXIF, its `moov` box has no Canon uuid box.
- **`jpeg.ErrExtendedXMPConflict`, `jpeg.EncodeKeptExtended`, `jpeg.ExtractFullSelectiveKept`, `xmp.WithExtendedLink`** (`format/jpeg/`, `xmp/jpegpackage.go`, #357): support for keeping extended XMP that could not be merged. `ErrExtendedXMPConflict` is returned when the XMP to write needs extended XMP of its own next to the segments that are kept.
- **`internal/bmff`** (`internal/bmff/openended.go`, #359): `OpenEnded`, `Close` and `CloseInPlace` give a box whose size field is 0 (extends to the end of its container, ISO/IEC 14496-12 §4.2) an explicit size; the one helper of the HEIF/AVIF and CR3 writers.
- **`exif.ExternalOffsets` and `exif.ExternalOffset`** (`exif/externaloffsets.go`, #362): find the MakerNote values that address data outside the EXIF stream (the Olympus PreviewImageStart and PreviewImageLength of CameraSettings), so the container writer can follow the data; `jpeg.Inject` uses it.
- **`internal/trailer`** (#322, #353, #354): the AFCP, FotoStation and Samsung trailer logic, moved out of `format/jpeg` so that `format/jpeg` and `format/tiff` share it.
- **`xmp.PackageForJPEG`, `xmp.JPEGPackage`, `xmp.StripExtendedLink`, `xmp.ErrTooLargeForJPEG`** (`xmp/jpegpackage.go`, #332): `PackageForJPEG` partitions an XMP value for a JPEG file as Adobe XMP Specification Part 3 §1.1.3.2 (p. 15) describes, adapted from the Adobe XMP Toolkit `XMPUtils::PackageForJPEG`: a standard packet of at most 65000 bytes and an extended serialisation without a packet wrapper, whose GUID is its uppercase MD5 digest. `StripExtendedLink` removes `xmpNote:HasExtendedXMP` from a packet.
- **`heif.ErrNoMetadataContainer`, `heif.ErrUnreadableItemLocations`** (`format/heif/errors.go`, #335): returned by `heif.Inject` (and so by `Write`) when a requested EXIF or XMP payload cannot be stored because the file has no valid `meta` box, or its `iloc` box is missing, unsupported, truncated or too large to rewrite.
- **`cr3.Segments.ExifIFD` and `cr3.ParseExifStream`** (`format/raw/cr3/cr3.go`, #336): `ExtractSegments` returns the CMT2 stream, and `ParseExifStream` parses it as the stand-alone TIFF stream it is: the Exif IFD and, when its `0xA005` pointer designates one, the Interoperability IFD.
- **`exif.MakerNoteLayout` and `(*EXIF).MakerNoteLayout()`** (`exif/makernote_parse.go`, #312, #310): report where the MakerNote IFD starts, its byte order, and whether its value offsets count from the TIFF header (`TIFFRelative`) or from inside the MakerNote. The TIFF-family writer uses it to rebase MakerNotes that move.
- **`cr3.Segments`, `cr3.ExtractSegments`, `cr3.ParseSubIFD`, `cr3.ErrBadCMTStream`** (`format/raw/cr3/cr3.go`, `format/raw/cr3/errors.go`, #300): `ExtractSegments` returns every metadata payload of a CR3 file (CMT1/CMT2 EXIF, CMT3 MakerNote, CMT4 GPS, XMP); `ParseSubIFD` parses the first IFD of a CMT3 or CMT4 stream and returns `ErrBadCMTStream` when the stream is not a readable TIFF stream.
- **`xmp.ParseExtended` and `xmp.ErrNoExtendedProperties`** (`xmp/extended.go`, #278): parse the standard XMP packet and the reassembled extended XMP of a JPEG file into one `*XMP`, keeping nested structures, qualifiers and array forms, and removing `xmpNote:HasExtendedXMP`. `ErrNoExtendedProperties` is returned when the extended document holds no property.
- **`xmp.ResolveAlias`, `xmp.Alias`, `xmp.AliasForm`** (`xmp/namespace_toolkit.go`, #307): resolve the 35 standard XMP aliases of the Adobe XMP Toolkit SDK to their base property (for example `photoshop:Caption` to the `x-default` item of `dc:description`). The lookup does not allocate.
- **`iptc.LookupDataset`, `iptc.DatasetInfo`, `iptc.DatasetFormat`** (`iptc/dataset_table.go`, #306): describe 116 IIM datasets of records 1, 2, 3, 7, 8 and 9 (name, value format, length bounds, repeatability, standard or not), transcribed from IIM 4.2 and cross-checked against bep/imagemeta. Binary-search lookup, about 6.7 ns/op, 0 allocations.
- **Third-party attribution** (`THIRD_PARTY_NOTICES.md`, `LICENSES/`, `docs/THIRD_PARTY.md`, `third_party_notices_test.go`, #298): one notice entry per project whose code or data is adapted, the full licence texts by SPDX identifier, and the `// Adapted from` file-header convention. `go test` fails when an adapted file is not listed or its licence text is missing. The root `LICENSE` is unchanged.
- **Eight fuzz targets** (#277, #278, #284, #301, #302, #308, #313, #314): `FuzzArtist` and `FuzzParseDates` (`internal/reconcile`), `FuzzIRB` (`internal/irb`), `FuzzIPTCDigest` (`internal/tiffscan`), `FuzzParseExtended` (`xmp`), `FuzzDecodeRawProfile`, `FuzzPNGExtractRawProfile` and `FuzzRewriteRawProfileIPTC` (`format/png`). The library now has 37 fuzz targets.
- **`exif.CarryThumbnailStrips`, `SubIFDs.ThumbnailStrips`** (`exif/thumbnail_strips.go`, `exif/chain.go`, #368): `Parse` with the option reads the strips of an uncompressed thumbnail of the 1st IFD (Exif 3.1 §4.5.8, Table 21) into `IFD.Sub.ThumbnailStrips`, and `Encode` and `EncodeRebased` write them after the IFD with a StripOffsets of the new positions. `Read` uses the option for every container that holds the EXIF stream on its own, and not for a TIFF-based file. See `docs/conformance/exif-tiff.md` S-50.
- **`exif.ExternalOffset.MNStart`, `.MNLen`, `.Target()`, `(*EXIF).ExternalOffsets`, `exif.ExternalOffsets(tiff, opts...)`** (`exif/externaloffsets.go`, #370): the Olympus preview offset in every form that real files use: CameraSettings stored as a value (E-1, E-300), the `0x1036`/`0x1037` and `0x0088`/`0x0089` pairs of the MakerNote IFD, and the `OLYMP\0` layout that counts from the TIFF header. `exif.ExternalOffsets` takes the parse options its stream needs (`AcceptRAWMagic` for an ORF). See R-31.
- **`(*EXIF).RebaseMakerNoteSubIFDs`** (`exif/makernote_rebase.go`, #370): sets the pointers inside the sub-IFDs of an Olympus `OLYMP\0` MakerNote for its new position in a TIFF-family stream. See R-36.
- **`xmp.ErrXMLTooComplex`, `exif.ErrCarriedDataTooLarge`, `png.ErrRawProfileBudget`** (`xmp/xmlscan.go`, `exif/private_ifd.go`, `format/png/rawprofile.go`, #376, #378, #381): new exported errors for input that exceeds a resource bound. `ErrXMLTooComplex` is returned by the XMP parser for a packet of more than 524288 elements or 1048576 attributes; `ErrCarriedDataTooLarge` by `EncodeRebased` when the MakerNote data and private IFDs it would carry exceed the shared allowance; `ErrRawProfileBudget` by PNG `Read` and `Write` when the raw profiles of a file inflate to more than 32 MiB together. See the Security section.

### Changed

- **Changed (compatibility notice): two exported constants changed value, for specification conformance.** Code that stores, compares or hard-codes either value must be updated. The module path is unchanged and the release is a minor version because the identifiers and signatures are the same.
  - `exif.TypeUTF8`: old value 13, new value 129. Reason: Exif 3.1 §4.6.2 (p. 28) defines UTF-8 as field type 129; code 13 is the TIFF IFD type of TIFF Technical Note 1, which is the new constant `exif.TypeIFD` = 13. An entry of type 129 now parses as a string, and type 13 is decoded as 4-byte IFD offsets.
  - `xmp.NSxmpNote`: old value `http://ns.adobe.com/xap/1.0/se/Note/`, new value `http://ns.adobe.com/xmp/note/`. Reason: Adobe XMP Specification Part 3 §1.1.3.1 and the XMP Toolkit `kXMP_NS_XMP_Note`. Packets that use the legacy URI are still read.
- **Performance: two measured regressions** (`benchmarks/BENCHMARKS.md`, v1.5.0 section): `BenchmarkReadCombinedMetadataJPEG` (EXIF, IPTC and XMP of a real JPEG) goes from 9.8 us and 39 allocations to 17.5 us and 56 allocations, from the XMP conformance work of #326 to #328 (well-formedness check, alias folding, verbatim text); `BenchmarkMWGAccessors` goes from 47 ns to 78 ns, from the table-driven reconciliation of #308. The TIFF write path allocates three more times per write (the image-block planner of the security fix F-07a) and is faster in ns/op. Bisected in `benchmarks/BENCHMARKS.md`; none comes from the sprint 47 security fixes.
- **BREAKING: `exif.TypeUTF8` is 129, not 13** (`exif/type.go`, `format/tiff/tiff.go`, `internal/tiffscan`, #320): Exif 3.0 and 3.1 define UTF-8 as field type 129 (Exif 3.1 §4.6.2, p. 28: "defined independently by this standard, rather than in TIFF6.0"); code 13 is the TIFF IFD type (TIFF Tech Note 1, libtiff `TIFF_IFD`), which is the new constant `exif.TypeIFD`. The value of the exported constant changes: code that stored `exif.TypeUTF8` in a file, compared it with a literal 13, or decoded type 13 as a string must be updated. - **EXIF: `EncodeRebased` carries every IFD0 pointer that is certain to address an IFD, not only `0x8290`** (`exif/private_ifd.go`, #370): entries of type IFD and the LONG tags `0x014A`, `0x0190`, `0x888A` and `0xFE00`, up to 10 offsets each. An unknown LONG is never carried. See R-32.

Not a defect, reported in #369: after a caption write of the Samsung Galaxy Note 4 corpus files ExifTool lists five MakerNote values that it does not list for the input. The MakerNote bytes are identical and ExifTool finds 7 entries in both; the camera stores IFD0 out of tag order (Make after the Exif IFD), which makes ExifTool take the note for unknown, and the output has IFD0 in the tag order that TIFF 6.0 §2 requires. See R-35.

Known limits found while verifying these fixes (not corrected here): the corpus Olympus `FE190/X750` TIFF (`ce50e53224a3b62bb821bc294bf6a588.tif`) has an `OLYMP\0` MakerNote whose offsets count from the MakerNote, which the TIFF writer rebases as TIFF-relative; `FuzzRewriteNikonMakerNoteIPTC` fails on a 284-byte input (`no tag 0x0E01`), also at the previous commit.

### Security

Findings of the 2026-10-16 pre-release security audit (rmp sprint 47, tasks #372 to #383). Each has a regression test named after its finding ID (`F-01` to `F-10`).

- **CRITICAL, F-01 (#372): a crafted HEIC panicked `Read`** (`format/heif/iloc.go`): the extent lengths of an iloc item were summed with an unchecked `uint64` addition, so `100 + (2^64 - 50)` wrapped to 50, a 50-byte buffer was allocated and the copy of the first extent sliced past it. The running total is now checked before each addition, and a copy that would not fit the buffer is an error.
- **F-09 (#382): a 168-byte HEIF made `Read` allocate 500 MiB** (`format/heif/iloc.go`): every extent is now checked against the length of the file (or of the `idat` payload) before the item buffer is allocated; the new error is `heif: metadata item data lies beyond the end of the file`.
- **F-02 (#373): `Write` of a HEIF with trailing boxes looped forever** (`format/heif/inject.go`): `patchAncestorSize` walked the whole file past the `meta` box, and a box with a zero or too small `largesize` never advanced. It now walks only the boxes that start before the `meta` box, bounds each size by the remaining length, and returns an error for a size below the box header (ISO/IEC 14496-12 §4.2).
- **F-03 (#374): AFCP trailer detection was quadratic** (`internal/trailer/trailer.go`): a 512 KiB trailer of repeated `AXS!` units took 15 s (30 s with the plan). The signatures are collected in one linear pass, at most 256 are examined, and the EOF record is looked up in that list; a valid trailer is found as before (BenchmarkFindAFCP valid-1MiB 22 µs to 11 µs, repeated-512KiB 3 µs). Shared with the TIFF trailer search.
- **F-04 (#375): XMP namespace resolution was quadratic** (`xmp/xmlscan.go`): resolving a prefix scanned every binding in scope, so N declarations and N `xml:lang` attributes cost O(N^2) (5.5 s for 3.4 MiB). A packet with more than 32 bindings in scope now uses a seeded hash index that grows with the scope (14.7 ms for the same input); ordinary packets keep the allocation-free scan.
- **F-05 (#376): an XMP packet of 3.9 million `<a/>` elements made `Read` allocate 3 GiB** (`xmp/xmlscan.go`): the element and attribute tables are capped at 524288 and 1048576, and the new `xmp.ErrXMLTooComplex` is returned beyond them. A packet inside the limits parses as before. The tables grow by doubling up to the cap; the 15 MiB packet now allocates 133 MiB instead of 3028 MiB before `ErrXMLTooComplex`.
- **F-10 (#383): XMP CDATA text was concatenated quadratically** (`xmp/xmlscan.go`): the CDATA sections of an element that follow other markup are chained and joined once.
- **F-06a (#377): the thumbnails of a long IFD chain multiplied on `Encode`** (`exif/ifd.go`, `exif/thumbnail_strips.go`): 500 chained IFDs addressing one 1 MiB range made a 1 MiB EXIF re-encode to 499 MiB. `Parse` now keeps the JPEG thumbnails (and the strips of an uncompressed thumbnail) of a whole parse only up to the length of the buffer, which disjoint thumbnails never exceed; a thumbnail beyond it is dropped with its offset entries and reported in `EXIF.Warnings`.
- **F-06b (#378): the private IFDs of IFD0 had no shared budget on `EncodeRebased`** (`exif/makernote_rebase.go`, `exif/private_ifd.go`): 40 entries addressing 16 MiB of values each re-encoded 15 MiB to 639 MiB. The MakerNote data and all private IFDs now share one allowance (the length of the source, 16 MiB at most) and at most 64 private IFDs are carried; the new `exif.ErrCarriedDataTooLarge` is returned beyond them.
- **F-07a (#379): duplicate TIFF strip blocks multiplied on `Write`** (`format/tiff/relocate_blocks.go`, `relocate.go`, `relocate_stream.go`): 2000 `StripOffsets` entries addressing one 1 MiB range wrote 2000 MiB. A write now coalesces overlapping and duplicate image-block ranges (strips, tiles, `JPEGInterchangeFormat`, SubIFD blocks), copies each source byte once and rebases every entry onto its place in the copy, so the copied image data is never more than the file. Valid files whose blocks overlap (a Sony ARW with one strip and 140 tiles over the same bytes, and several TIFFs with overlapping strips or a thumbnail inside a strip) are written; files with disjoint blocks produce the same bytes as before. A block outside the file is still rejected with `tiff.ErrBlockOutOfBounds`.
- **F-07b (#380): the SubIFDs that next-IFD pointers link bypassed the image block budget** (`format/tiff/relocate.go`): 1024 heads of 512-IFD chains allocated 206 MiB for a 3 MiB file. Each SubIFD built is charged 4 units, and `tiff.ErrTooManyImageBlocks` is returned when the budget runs out (18 MiB allocated before the error).
- **F-08 (#381): every PNG raw profile chunk was inflated on `Read` and `Write`** (`format/png/png.go`, `format/png/rawprofile.go`): 40 chunks of 63 MiB cost 2.1 s of CPU. A profile of a kind that an earlier chunk supplied is no longer inflated, and the profiles of one file may inflate to 32 MiB together; the new `png.ErrRawProfileBudget` is returned beyond that (18 ms for the same file).

## [1.4.0] - 2026-09-26

### Added

- **`format/tiff` streaming `Inject` variants**: `InjectWithEXIFStream`, `InjectWithEXIFCR2Stream`, `InjectWithEXIFNEFStream`, `InjectWithEXIFARWStream`, `InjectWithEXIFORFStream`, and `InjectWithEXIFRW2Stream` expose the streaming image-data-relocation path introduced by #291 below (image blocks are fetched from an `io.ReadSeeker` instead of being buffered whole) under new, dedicated names. The pre-existing `InjectWithEXIF*` functions keep their exact v1.3.0 signature — an apidiff run against v1.3.0 caught that #291 had accidentally changed it, which would have been a breaking change in a minor release — and are now thin wrappers over their `*Stream` sibling (`bytes.NewReader(originalBytes)`, `wholeFile=true`). The root `Write` path already calls the `*Stream` variants directly, so none of the performance improvements documented below are affected.
- **`(*Metadata).RawSegments()`**: returns zero-copy, read-only views of the raw EXIF, IPTC, and XMP segment bytes exactly as stored on `m`, for allocation-sensitive callers (e.g. hashing or comparing raw bytes across many images) that don't need an independently owned copy. Unlike `RawEXIF`/`RawIPTC`/`RawXMP`, the returned slices alias `m`'s own internal storage — the caller must not modify, append to, or retain them past any subsequent mutation of `m` (a `Set*` call or `Write`).
- **`exif.AcceptRAWMagic`, `exif.AliasThumbnail`, `exif.EncodeInto`, `exif.EncodedSize`**: new `exif` package exports supporting the read/write performance work below — `AcceptRAWMagic` and `AliasThumbnail` are opt-in `ParseOption`s (the latter aliases `IFD.ThumbnailData` directly into the parse buffer instead of copying it, under a documented buffer-lifetime contract); `EncodeInto` and `EncodedSize` let a caller size and fill its own output buffer instead of receiving a freshly allocated one from `Encode`.
- **`format/jpeg.ExtractFullSelective`, `format/tiff.ExtractWithMagic`**: new package-level entry points supporting selective (IPTC/XMP-only) extraction and RAW-magic-aware TIFF extraction, used internally by the top-level `Read` path.

### Fixed

- **`format/tiff` public API compatibility restored**: Sprint 44's streaming-write refactor (see the "Performance" items under Changed below) had inadvertently changed the signatures of the six exported `InjectWithEXIF*` functions in `format/tiff` — a breaking change that would have violated this project's SemVer commitment in a minor release. Caught by an `apidiff` comparison against v1.3.0 run as part of this release's pre-flight; fixed by restoring the original v1.3.0 signatures as thin wrappers over the new `*Stream` variants (see "Added" above). A follow-up commit also restored two `//nolint:gosec` (G115) suppression comments that the same refactor had dropped from `exif/ifd.go` and `format/tiff/relocate_bigtiff.go`; both underlying integer conversions remain provably bounds-safe (verified by code review) — this is a lint-hygiene restoration with no behavioural change.

### Changed

- **`Metadata.RawEXIF()` returns a metadata prefix, not the whole file, for TIFF/CR2/NEF/ARW/DNG/ORF/RW2** (`format/tiff/extent.go`, `format/raw/orf/orf.go`, `format/raw/rw2/rw2.go`, `metadata.go`, #289 for TIFF/CR2/NEF/ARW/DNG; #293 for ORF/RW2): for these seven formats — the ones where the TIFF byte stream is itself the EXIF container — `Read` now reads and `RawEXIF()` now returns only the portion of the file needed to describe metadata (every IFD in IFD0's next-IFD chain, `ExifIFD`, `GPSIFD`, `InteropIFD`, and `SubIFDs`, plus every out-of-line tag value within them, including MakerNote blobs and the tag payloads `RawIPTC()`/`RawXMP()` read from), not the strip/tile image-data blocks or embedded thumbnails/previews that make up the overwhelming majority of a real file's bytes. `m.EXIF`, `RawIPTC()`, and `RawXMP()` are unaffected: every tag they report is identical to a whole-file read. `Write`/`WriteFile` are unaffected: the TIFF-family write paths transparently re-read the full source from the original `io.ReadSeeker` for image-data relocation whenever `RawEXIF()`'s content is only a prefix (reusing it directly, with no second read, on the inputs where the prefix scan happened to read the whole file anyway). Formats other than these seven (JPEG, PNG, WebP, HEIF/AVIF, CR3) are unaffected — `RawEXIF()` already returned just the EXIF segment/box/chunk for those, never the whole file.
- **PNG `Read`/`Extract` no longer rejects a file whose declared chunk length overruns the stream** (`format/png/png.go`, #294): when a chunk's declared length would extend past the end of the file — whether the chunk would have been skipped (an ancillary type `Extract` does not interpret) or read for its metadata content — `Extract` now stops scanning at that point and returns whatever metadata had already been collected, with a `nil` error, instead of rejecting the file. This restores the pre-#288 behaviour for files whose metadata precedes the truncated/malformed tail of the stream. `Write`/`WriteFile` (`Inject`) are unaffected and continue to reject a truncated PNG outright: silently dropping trailing content on a caller-requested write remains unsafe in a way a best-effort read is not.
- **Performance: `Write`/`WriteFile` no longer buffer the whole source file for CR3, TIFF, DNG, CR2, NEF, ARW, ORF, or RW2** (`format/raw/cr3/cr3.go`, `format/tiff/relocate*.go`, `format/tiff/tiff.go`, `internal/iobuf/streamcopy.go`, `write.go`, #291/#292; see `BENCHMARKS.md` "Batch G" for full benchstat detail): CR3's `Inject` now rebuilds only the `moov` box in memory and streams `ftyp`/`mdat`/every other box verbatim from the source through a new pooled-buffer primitive (`iobuf.StreamCopyN`), instead of reading the whole file and building a second, equally large output buffer (Write B/op on a 12 MB Canon CR3: ~24.7 MiB → ~217 KiB). The TIFF-family copy-and-relocate serialiser now separates the small, metadata-sized IFD structure it rebuilds from the (routinely much larger) image-data blocks it relocates, streaming the latter directly from the source reader for every one of the seven TIFF-based formats (Write B/op on real corpus files: TIFF ~849 KiB → ~25 KiB, CR2 ~46 MiB → ~139 KiB, DNG ~49 MiB → ~655 KiB). NEF, ARW, ORF, and RW2 each carry one manufacturer-specific metadata structure outside the generic IFD/SubIFD scan — Sony `SR2Private`, Nikon's MakerNote-embedded `PreviewIFD`, Olympus's OLYMP-type external `ThumbnailImage`, Panasonic's `RawDataOffset`-to-EOF convention — and now fetch only that small extra byte range on demand from the source reader (a bounded `Seek`+`ReadFull`, never the whole file) instead of requiring a full-file read; every image-data block, including RW2's `RawDataOffset`-to-EOF region, still streams directly from the source. No output byte ever changes: `Write`'s output is verified byte-for-byte identical to the prior implementation across the full corpus.
- **Performance: `exif.Encode` no longer double-buffers an IFD's out-of-line value area** (`exif/ifd.go`, task #291 follow-up): `writeIFD`/`writeIFDBigTIFF` previously built each IFD's out-of-line value area in a separate slice and then copied it into the caller's output buffer via `append(out, valueArea...)` — paying for the value area's full byte count twice, negligible against a whole-file write buffer but the dominant remaining Write allocation once the change above shrank every TIFF-family format's own Write buffer to metadata-prefix scale (a real camera file's IFD can carry a multi-hundred-KB-to-multi-MB out-of-line value area, e.g. an embedded MakerNote blob copied through verbatim). Both functions now compute the value area's exact final length in a first pass over the IFD's entries, then append every out-of-line value's bytes directly into the (once pre-grown) output buffer in a second pass, eliminating the intermediate buffer entirely. This is reached by every format that embeds EXIF, not only the seven TIFF-family containers, whenever `m.EXIF` is modified before `Write`. Output is unaffected: verified byte-for-byte identical across the full corpus.
- **Fixed: `format/tiff` metadata-prefix scanner over-read large-but-stable-fraction files** (`format/tiff/extent.go`, task #293 follow-up): the scanner's large-fraction snap forced a full-file read whenever a single pass's need reached 10% of the file's size, even when that fraction was already stable (not still growing across passes) — e.g. `raw/metadata-extractor/OM System TG-7.ORF`, whose real metadata need is a stable 11.5% of its 13.15 MB file, was read in full instead of the true ~1.5 MB prefix. A corpus-wide A/B simulation across all 114 real TIFF-family corpus files above the 4 MiB whole-file-read threshold found removing this snap regressed zero files' pass count or final buffer size while shrinking the corpus-wide average converged buffer 42%; the snap is removed rather than replaced with a different threshold.
- **Performance: `format/tiff`'s metadata-extent scanner no longer allocates a cycle-detection map on every growth pass** (`format/tiff/extent.go`, task #291/#293 follow-up): `scanExtentPass` previously allocated a fresh `*extentScan` (holding a `seenIFD map[uint64]bool`) every time `scanMetadataExtent`'s growth loop ran, scaling allocs/op with however many passes a file's IFD chain needed to converge (2–3 for a typical NEF/ARW/RW2/ORF). One `*extentScan` is now allocated once per `Extract`/`Read` call and reused across passes, with `scanExtentPass` resetting (`clear`ing, never reallocating) its `seenIFD` map before each pass — clearing between passes is required for correctness (a pass that stopped early must let the next, larger-buffer pass revisit the same IFD from scratch), not just an optimisation. Read allocs/op: NEF 26 → 22, ARW 28 → 24 (exact parity with the pre-metadata-prefix-scanning baseline), DNG 39 → 35, RW2 21 → 17, ORF 27.2 → 24.

- **Performance: `iobuf.StreamCopyN` moves bytes once instead of twice for two specific, safe-to-detect endpoint types** (`internal/iobuf/streamcopy.go`, task #297): when the sink is `*bytes.Buffer`, `(*bytes.Buffer).ReadFrom` now reads directly into the buffer's own backing array (bounded to the exact byte count via a pooled `*io.LimitedReader`, so no allocation is added) instead of the pooled-scratch-buffer loop's read-then-copy-again; when the source is `*bytes.Reader` and the requested byte count equals its own remaining length, `(*bytes.Reader).WriteTo` writes its zero-copy internal slice directly to the sink in one call. Every other `(reader, writer)` pair — in particular file-to-file, unaffected and unchanged — keeps the original pooled-buffer loop: a generic "use `io.CopyN` whenever the sink implements `io.ReaderFrom`" prototype was measured 31–38% slower file-to-file on darwin, since `(*os.File).ReadFrom` falls back to `io.Copy`'s own small internal buffer. `BenchmarkWrite/{cr2,nef,dng,orf,rw2,cr3}` (e2e harness, in-memory reader and `*bytes.Buffer` sink — a common calling pattern for `Write`) are 32–51% faster with identical allocs/op; a new file-to-file benchmark shows no measurable regression.
- **Performance: every EXIF `Read` no longer allocates its `exif.ParseOption` slice or the option closures themselves** (`read.go`, `exif/exif.go`, task #297): `parseEXIF` previously built its options via `append(nil, ...)`, and each of `exif.SkipMakerNote`/`AcceptRAWMagic`/`AliasThumbnail` — non-capturing closures Go would normally represent as static, non-allocating values — escaped to the heap once inlined into `parseEXIF` (a Go compiler quirk specific to a non-capturing closure literal fed into `append`/a variadic call once inlined). Fixed by marking the three option constructors `//go:noinline` (restoring the static-closure optimisation at their own, un-inlined call site) and assembling `parseEXIF`'s options via a fixed-size array with direct indexed assignment instead of a growing nil slice. No public API change. `BenchmarkRead/tiff` and `BenchmarkRead/jpeg_exiftool` allocs/op: 10 and 39 (both −1 from before).

### Security

- **CRITICAL: BigTIFF `off+size` overflow panic in the copy-and-relocate write path closed** (`format/tiff/relocate.go`, `format/tiff/relocate_stream.go`, `format/tiff/relocate_bigtiff.go`, `exif/ifd.go`, new `internal/boundscheck` package): several bounds checks computed `end := off + size` as a raw, unchecked `uint64` addition before comparing `end > fileLen`. A BigTIFF file declaring StripOffsets/StripByteCounts (or a SubIFD entry's value area) as LONG8 (8-byte) fields could set an offset near `MaxUint64`, wrapping the addition to a small value that incorrectly passed as "in bounds" and then panicked on a subsequent slice expression — reachable from untrusted input via `Write`/`WriteFile` on any BigTIFF source. Bisected to 0ebf5d4 (pre-dating Sprint 44). A second, independently reachable instance was found on the **Read** path (`exif.extractJPEGThumbnail`, a `TypeLong8` `JPEGInterchangeFormat` offset) — no `Write` call required, triggered by any top-level `Read`/`ReadFile` of a crafted file. Every affected comparison now routes through a single shared, overflow-safe helper (`internal/boundscheck.Fits`) instead of a raw addition; two sites additionally needed an overflow-safe multiplication guard (`count*elemSz`) since the count itself is an attacker-controlled BigTIFF LONG8 field. See `BENCHMARKS.md`'s "Security fix" entry for the full list of sites and the PoC (CWE-190, CWE-125, CWE-787).

## [1.3.0] - 2026-07-07

### Added

- **BigTIFF write support, end to end** (`exif/write.go`, `format/tiff/relocate_bigtiff.go`, `write.go`, tasks #264/#270/#271): `exif.Encode` now natively encodes BigTIFF-sourced EXIF (`EXIF.BigTIFF == true`) with a 16-byte header, 20-byte IFD entries, and 64-bit offsets throughout (BigTIFF spec §2, Aware Systems/libtiff); `format/tiff`'s copy-and-relocate serialiser is now container-width-aware end to end (image-block enumeration, `SubIFDs` 0x014A relocation, and every raw-offset scan performed after encoding), so a standalone BigTIFF file relocates correctly on write; and the top-level `Write`/`WriteFile` no longer refuse BigTIFF sources with `ErrWriteNotSupported` — the root-package guard has been removed now that both layers are verified end-to-end against real BigTIFF corpus fixtures (LONG8/SLONG8/IFD8 strip/tile arrays, multi-level SubIFD chains, and the committed `BigTIFF_LE.tif`/`BigTIFF_BE.tif`/`big_cramps_{be,le}.tif` fixtures). Two new sentinel errors guard the encode path: `exif.ErrBigTIFFPointerOverflow` (a sub-IFD or thumbnail pointer — fixed by spec to a 4-byte EXIF LONG field regardless of container — would need an absolute offset that does not fit in 32 bits) and `exif.ErrBigTIFFEncodeSizeExceeded` (the encoded payload would exceed a documented, test-overridable 4 GiB sanity ceiling, since BigTIFF's 64-bit offsets have no implicit `MaxUint32` saturation the way classic TIFF's do). `exif.ErrBigTIFFEncodeNotSupported` is no longer returned by `Encode` under normal conditions and its doc comment now marks it **Deprecated**; it is retained only for API compatibility and may be removed in a future major release. `ErrWriteNotSupported` remains exported for any future format without a write path.

- **XMP `geo:` namespace prefix** (`xmp/namespace.go`): `xmp.Encode` now emits the conventional `geo:` prefix for the W3C Basic Geo namespace (`http://www.w3.org/2003/01/geo/wgs84_pos#`) instead of a generated `nsN:` placeholder, matching the prefix that `xmp.GPS()`'s W3C-Geo fallback (added in v1.2.0) already expects when reading it back.
- **Write-path (`*Inject`) fuzz targets for JPEG, PNG, and all seven RAW formats** (#258): `FuzzJPEGInject`, `FuzzPNGInject`, `FuzzARWInject`, `FuzzCR2Inject`, `FuzzCR3Inject`, `FuzzDNGInject`, `FuzzNEFInject`, `FuzzORFInject`, and `FuzzRW2Inject` each round-trip Extract → mutate → Inject → Extract and assert the library never panics on untrusted input; `FuzzCR3Inject` is seeded with the extended-size `moov`/`uuid` byte sequences that exposed the fix described below. This closes a gap where every write path except TIFF, HEIF, and WebP had read-only fuzz coverage; the library now ships exactly 29 fuzz targets (see `SECURITY.md` for the full, verified inventory).
- **`iptc.ErrDatasetValueTooLarge`**: new exported sentinel returned by `iptc.Encode` when a `Dataset.Value` is longer than the extended-length header can represent (4 GiB − 1, IIM §1.6.2 extended-length form). Callers can use `errors.Is` to distinguish this from other encode failures.
- **`format/tiff.ErrTooManyImageBlocks`**: new exported sentinel returned by the TIFF-family write/relocate path (TIFF, DNG, CR2, NEF, ARW, ORF, RW2) when a single `StripOffsets`/`TileOffsets`/SubIFD-pointer entry, or the aggregate across all such entries in one write, declares more image blocks than the new spec-justified caps allow.

- **`format/jpeg.ErrFileTooLarge`**: JPEG gains the same 256 MiB aggregate-size cap already enforced by every other container package (`webp`, `heif`, `orf`, `rw2`, `cr3`, `tiff`).

### Changed

- **Performance: EXIF parse and encode hot paths** (tasks #198–#203, #240; see `BENCHMARKS.md` for full benchstat detail): `exif.Parse` uses a lazy sub-IFD arena that co-allocates all sub-IFD structures in a single batch when `ExifIFD`/`GPSIFD` are present (measured −25% allocs/op on camera-file EXIF at the time the task landed); `IFDEntry`'s byte-order field is now a 1-byte flag instead of a 16-byte `binary.ByteOrder` interface (`unsafe.Sizeof(IFDEntry{})` 56 B → 48 B); warning-string construction is deferred from the IFD-traversal hot path to the `Parse` boundary, removing `fmt.Sprintf` from the common (warning-free) case; the fixed-array staging buffers in `writeTIFFHeader`/`writeIFD` no longer escape to the heap; MakerNote dispatch no longer allocates a string via `(*IFDEntry).String()` to build its map key; and the EXIF encode path pools its `filterEntries` scratch slices via a package-level `sync.Pool`. Net effect at HEAD: `BenchmarkEXIFEncode` 2 allocs/op (down from 6 at the v1.2.0 baseline).
- **`exif.EXIF` and `xmp.XMP` concurrency contract documented** (#245, XMPCONC-01): both types' doc comments now explicitly state they are not safe for concurrent mutation from multiple goroutines without external synchronisation, mirroring the existing `iptc.IPTC` note. `Metadata`'s own concurrency contract (an internal mutex guarding every `Set*` call) is unaffected; this clarifies the boundary for callers who mutate `m.EXIF`/`m.XMP` directly instead of through `Metadata.Set*`.
- **`format.Detect` now uses `io.ReadFull`** (#244) instead of a single `Read` call, so a chunking reader (a socket, `io.Pipe`, a decompressing stream, or a small `bufio.Reader`) that satisfies a short read mid-stream is no longer misdetected as `FormatUnknown`.
- **EXIF byte-order resolution corrected** (#246, #252): `ifd0ByteOrder()` now prefers the authoritative `EXIF.ByteOrder` field instead of inferring order from `IFD0.Entries[0].bigEndian`, and `IFD.set()` now takes an explicit big-endian flag instead of inheriting it from `Entries[0]`. Previously, a spec-legal big-endian file with an empty IFD0, or a freshly created `ExifIFD`/`GPSIFD`, could cause the numeric `Set*` methods and the `GPS`/`ExposureTime`/`FNumber`/`ISO`/`FocalLength`/`ImageSize` accessors to silently read or write little-endian bytes into a big-endian structure.

### Fixed

- **HEIF `iloc` 5-byte body out-of-bounds panic** (#243): `parseIloc` and `parseIlocFull` guarded the `iloc` body length with `len < 5`, but both read a second size-nibble byte at index 5; a minimal legal 5-byte `iloc` body (box size 13, ISO 14496-12 §8.11.3) passed the guard and then panicked. Both guards are now `len < 6`.
- **HEIF `iloc` extent-count memory/CPU amplification** (#249): `readIlocFullExtents`/`readIlocSimpleExtents` iterated the full attacker-controlled `extent_count` (up to 65 535) even in the degenerate case where every field-size nibble is zero and each iteration consumes zero input bytes. The extent count is now capped at `maxIlocExtentsPerItem` (1024) per item, the zero-field-size loop is bounded to the same cap, and the outer item count is capped at `maxIlocItems` (4096), mirroring the existing BigTIFF IFD0 item cap.
- **HEIF 32-bit offset-arithmetic slice panic** (#257): `extractExifFromData` and `parseIinfItemCount` narrowed an attacker-controlled `uint32` offset to `int` before bounds-checking; on 32-bit platforms (`GOARCH=386/arm/mips`) an offset ≥ `0x80000000` wrapped negative and bypassed the guard, producing a negative-index slice panic. Both sites now compare in `uint64` before narrowing.
- **CR3 extended-size box headers mishandled in `Inject`** (#256): `cr3.Inject` hard-coded an 8-byte box header when locating the `moov`/Canon `uuid` boxes, silently mis-slicing (and dropping metadata siblings from) any source using the ISO/IEC 14496-12 §4.2 extended 16-byte header form (`size == 1` followed by an 8-byte `largesize`). The header length is now re-derived via `parseCR3BoxHeader` at both slice sites, and `flatUUIDBoxRange` gained a missing bounds guard against an undersized `uuid` box.
- **ORF/RW2 double-write corruption** (#250): `writeTIFFORF`/`writeTIFFRW2` passed `m.EXIF` directly to the mutating relocator instead of a clone, so calling `Write` twice on the same `*Metadata` silently corrupted image data on the second call. Both now clone the EXIF struct first, matching the fix already applied to every other format in v1.2.0 (#109).
- **EXIF IFD-chain traversal unbounded** (#255, EXIF-IFDCHAIN-01): a crafted EXIF/TIFF payload with a chain of overlapping IFD offsets, each declaring a large entry count, could force multi-gigabyte retained heap and multi-second CPU from a sub-megabyte input. `Parse` now shares a `traverseBudget` across the IFD0 chain and all sub-IFD traversals: chain length is capped at `maxTraverseChainIFDs` (512 IFDs), and cumulative entries parsed are capped at `max(len(b)/6, 64)` and charged using the pre-deduplication entry count so a duplicate-tag IFD cannot evade the budget.
- **TIFF-family write/relocate path unbounded allocation, GM-W1** (#261): `extractParallelOffsetBlocks` and `enumerateSubIFDsAt` allocated one heap object per declared `StripOffsets`/`TileOffsets`/SubIFD-count element with no upper bound, so a crafted sub-256 MiB TIFF/DNG/CR2/NEF/ARW/ORF/RW2 file could drive multi-gigabyte allocation through a plain read-then-write round trip with no metadata modification required. New per-entry (`maxImageBlocksPerOffsetEntry` = 65536; `maxSubIFDsPerEntry` = 1024) and aggregate (`maxAggregateImageBlocks` = 262144) caps now reject oversized declarations with `format/tiff.ErrTooManyImageBlocks` before any allocation.
- **`WriteFile` propagated `setuid`/`setgid`/sticky bits to rewritten output** (#259): the atomic-replace path preserved the source file's full mode via `Chmod`, including any `setuid`/`setgid`/sticky bits already present. These are now masked off the replacement file while ordinary permission bits are still preserved.
- **TIFF/ORF/RW2/CR3 32-bit offset truncation in IFD0 lookup** (#253): `findExifIFDOffset` (in `format/tiff`, `format/raw/orf`, `format/raw/rw2`) and CR3's `mergeCMT` compared an offset after narrowing it to `int`; on 32-bit platforms an offset ≥ 2³¹ narrowed to a negative `int`, passed the length guard, and then panicked on slicing. The comparison is now performed in `uint64` before narrowing.
- **`writeTIFFHeader`/`writeIFD` panicked on a non-standard `binary.ByteOrder`** (#247, PERF-201-LOW): a non-comma-ok type assertion to `binary.AppendByteOrder` (introduced by the byte-order refactor in v1.2.0) panicked for any `binary.ByteOrder` implementation other than the two standard-library singletons. The assertion is now comma-ok with a `PutUint16`/`PutUint32` fallback; the little-/big-endian fast path is unchanged and remains zero-allocation.
- **IPTC `Encode` extended-length overflow**: a `Dataset.Value` longer than the 4-byte extended-length field can represent was silently truncated to its low 32 bits while every value byte was still written, desynchronising the encoded stream. `Encode` now rejects such values with `iptc.ErrDatasetValueTooLarge` (see Added) instead of emitting a wrapped length field.
- **TIFF SubIFD type-13 (`IFD`) misparsed as UTF8** (part of #270): `format/tiff`'s relocator trusted `exif.Parse`'s type-13 decoding for tag `0x014A` (`SubIFDs`), but CIPA DC-008-2023's EXIF-3.0 assignment of `TypeUTF8` to the same numeric code as the legacy TIFF-extension `IFD` type meant a SubIFD pointer array declared as type 13 was silently corrupted or dropped on write. The relocator now re-scans the raw bytes for this tag directly instead of trusting the parsed struct.
- **XMP array-typed property container-type round-trip fidelity, plus Dublin Core allowlist gaps** (#272/#273, `xmp/namespace.go`, `xmp/rdf.go`, `xmp/write.go`, `xmp/xmp.go`): `collectionType`/`isCollectionProperty` were two independently maintained switch statements that had already drifted out of sync, and recognised only 5 of the 11 array-typed `dc:` properties (`creator`, `subject`, `title`, `description`, `rights`); a single-value `Set(NSdc, "contributor", ...)` — and `date`/`language`/`publisher`/`relation`/`type` — previously emitted a bare scalar element instead of the `rdf:Bag`/`rdf:Seq` container required by ISO 16684-1 §7.5. Both switches are now consolidated into one spec-sourced `arrayProperties` table covering all 11 `dc:` properties plus every other array-typed property across `xmpMM`, `xmpRights`, `xmp`, `tiff`, `exif`, `photoshop`, `Iptc4xmpCore`, and `Iptc4xmpExt`. The same consolidation corrects `xmpMM:Ingredients`/`xmpMM:Pantry` — previously wrongly coded as ordered `Seq` — to the spec-correct unordered `Bag` (Adobe XMP Specification Part 2 §1.2.8), and adds the previously-missing `xmpMM:Versions` (`Seq`). More fundamentally, a plain `Parse` → (unrelated field write) → `Encode` round trip previously downgraded *any* array-typed property outside this table's namespace/name coverage to a bare scalar, because the spec table was the sole authority `Encode` consulted — violating this project's "existing metadata is preserved exactly" mandate for every namespace the table does not (and, being finite, never can) enumerate. `XMP` now records the RDF collection kind (`Seq`/`Bag`/`Alt`) actually observed at parse time in a new unexported `containerTypes` map, consulted first on `Encode`, falling back to the spec table only for properties with no parse-time record (i.e. newly `Set()`). As a side effect, this also fixes a single-item `rdf:Alt` property outside the table leaking its internal `"lang|value"` storage separator into the serialised output text.
- **XMP numeric character references admitted XML 1.0 forbidden code points** (#274, `xmp/rdf.go`): `decodeCharRef` accepted any numeric character reference (`&#N;` / `&#xHH;`) whose value was a legal Unicode scalar value, even when that value falls outside the XML 1.0 §2.2 `Char` production — the C0 control block other than TAB/LF/CR, and the two BMP non-characters U+FFFE/U+FFFF. For U+001E specifically — this library's own internal multi-value record separator — a crafted-but-parseable document containing `&#x1e;` could cause `Encode` to spuriously re-serialise a genuinely scalar/Simple property as an `rdf:Bag`. `decodeCharRef` now substitutes U+FFFD for any such forbidden code point, matching the identical policy `writeXMLEscaped` already applies on the output side, so parsing and serialisation are consistent in both directions.
- **BigTIFF write is now fully supported through the public API** (`write.go`, `exif/write.go`, `format/tiff/relocate.go`, `format/tiff/relocate_bigtiff.go`, #264/#270/#271) — see Added for the full description.
- **XMP encoder now always wraps array-typed properties in their RDF collection container** (`xmp/write.go`, `xmp/namespace.go`): `dc:creator`, `dc:subject`, `dc:description`, `dc:rights`, `dc:title`, and the `xmpMM` ordered-array set (`History`, `Ingredients`, `Pantry`) are now serialised as `<rdf:Seq>`/`<rdf:Bag>`/`<rdf:Alt>` even when they hold exactly one value, per ISO 16684-1 §7.5. Previously, a single-item array-typed property (e.g. the common case of `SetCaption`/`SetCreator` writing exactly one value) was serialised as a bare `<prefix:local>value</prefix:local>` element, which is only correct for Simple (Text) properties. Round-trip value correctness (via this library's own lenient parser) was unaffected, but the produced wire format did not conform to the formal Lang-Alt/array schema that other XMP consumers expect.

### Security

- **HEIF CRITICAL: `iloc` 5-byte body OOB panic closed** (#243): a slice-bounds-out-of-range panic reachable from untrusted HEIF/AVIF input via the public `heif.Extract` and `heif.Inject` paths (and therefore the top-level `Read`/`Write`) is now closed (CWE-125, CWE-787).
- **HEIF HIGH: `iloc` extent-count amplification closed** (#249): an attacker-controlled extent count could amplify a small HEIF/AVIF file into multi-gigabyte allocation on `Inject` or unbounded CPU on `Extract`; both are now bounded (CWE-770, CWE-834).
- **HIGH: OOM guard added to the TIFF-family root `Write` paths** (#251): the six TIFF-family write paths (`TIFF`, `DNG`, `CR2`, `NEF`, `ARW`, `ORF`, `RW2`) now cap the total bytes read from an untrusted `io.Reader` at 256 MiB via the new root `ErrFileTooLarge`, closing an OOM vector that the v1.1.0 `io.ReadAll` guard (#140) missed at these specific root-package call sites (CWE-770).
- **HIGH: TIFF-family write/relocate allocation DoS closed, GM-W1** (#261): a crafted sub-256 MiB file could force multi-gigabyte allocation through a plain read-then-write round trip with no metadata modification; per-entry and aggregate caps now reject the request before allocation (CWE-770, CWE-405).
- **HIGH: ORF/RW2 double-write corruption closed** (#250): calling `Write` twice on the same `*Metadata` for an ORF or RW2 source silently corrupted image data on the second call, with no error returned (CWE-664).
- **MEDIUM: `format.Detect` short-read misdetection closed** (#244): a chunking reader (socket, `io.Pipe`, decompressing stream, small `bufio.Reader`) could cause a valid image to be misdetected as `FormatUnknown`, failing every subsequent `Read`/`Write` call for that caller — a soft denial of service (CWE-20).
- **MEDIUM: EXIF byte-order inference corrected** (#246, #252): a spec-legal big-endian EXIF file with an empty IFD0, or a freshly created sub-IFD, could cause numeric setters and accessors to silently read or write little-endian bytes into a big-endian structure, corrupting output with no error surfaced (CWE-198).
- **CR3 extended-size box mishandling closed** (#256): a CR3 source using the ISO/IEC 14496-12 extended 16-byte box header form could have its EXIF and/or pre-existing metadata siblings silently dropped by `Inject`, with no error returned (CWE-682, CWE-390).
- **HEIF/TIFF/ORF/RW2/CR3 32-bit offset-arithmetic panics closed** (#253, #257): several offset comparisons narrowed an attacker-controlled 32-bit or 64-bit file offset to a platform `int` before bounds-checking, producing a negative-index slice panic on 32-bit builds (`GOARCH=386/arm/mips`); all affected sites now compare in `uint64` before narrowing (CWE-681, CWE-190, CWE-129).
- **EXIF IFD-chain traversal resource-exhaustion DoS closed** (#255): a crafted chain of overlapping IFD offsets could force gigabytes of retained heap and multi-second CPU from a sub-megabyte input; traversal is now bounded by both chain length and cumulative entry count (CWE-400, CWE-405, CWE-834).
- **LOW: `writeTIFFHeader`/`writeIFD` panic on non-standard `binary.ByteOrder` closed** (#247): a non-comma-ok type assertion could panic when the library is used with a caller-supplied `binary.ByteOrder` implementation instead of the two standard-library singletons (CWE-704).
- **`WriteFile` no longer propagates `setuid`/`setgid`/sticky bits to rewritten output** (#259): a metadata rewrite can no longer (re-)create a privilege-escalation surface, even when only preserving bits already present on the source file. The write trust boundary — `WriteFile`'s symlink-following behaviour and the streaming `Write`'s partial-output-on-error behaviour — is now documented in `SECURITY.md`.
- **IPTC extended-length overflow closed** (`iptc.Encode`): a `Dataset.Value` too long for the 4-byte extended-length field to represent was previously truncated silently rather than rejected, which could desynchronise the encoded stream; `Encode` now returns `iptc.ErrDatasetValueTooLarge` (CWE-190).
- **BigTIFF encode size ceiling added** (`exif.ErrBigTIFFEncodeSizeExceeded`): BigTIFF's 64-bit offset fields have no natural saturation ceiling the way classic TIFF's 32-bit fields do; `Encode` now enforces an explicit, documented, test-overridable 4 GiB sanity ceiling on the total encoded size before allocating the output buffer, preventing a pathological `IFDEntry.Count` from directing an unbounded allocation (CWE-400).
- **INFO: `format/jpeg` 256 MiB aggregate size cap added** (#262): JPEG now enforces the same project-wide aggregate input cap as every other container format, closing a defense-in-depth gap — JPEG was the only container package without one. Per-APP-segment lengths were already 16-bit bounded, so this is a normalisation rather than a fix for a known amplification bug.
- **LOW: XMP numeric character references could carry XML 1.0 forbidden code points** (#274): a crafted document containing a numeric character reference to a C0 control code point (other than TAB/LF/CR) or a BMP non-character (U+FFFE/U+FFFF) — including this library's own internal `\x1e` multi-value sentinel byte — was decoded verbatim instead of being replaced, extending the existing C0 control-character filtering (#170/#171) to this parse path. `decodeCharRef` now applies the identical U+FFFD substitution policy already used on the output side (CWE-91).

- **`internal/iobuf` undersized-buffer pool return** (#186/#187): `iobuf.Put` now correctly returns buffers whose capacity exceeds the small-tier threshold but is within the large-tier cap to the large pool, rather than discarding them. This halves allocations on large-buffer cache-miss paths.
- **RIFF bounds contract enforcement** (#192): the internal `riff` package now enforces the invariant that a chunk body slice cannot extend beyond the parent list boundary, preventing cross-chunk reads in WebP and other RIFF-based containers.
- **XMP W3C Geo GPS namespace decoding** (#195): `xmp.GPS()` previously returned zero coordinates for files using the W3C Geo namespace (`http://www.w3.org/2003/01/geo/wgs84_pos#`) for GPS properties. The namespace is now recognised alongside the standard EXIF `GPS` namespace.
- **`metadata.Set*` mutex guard** (#128/#148/#185): all `Set*` methods on `*Metadata` are now protected by an internal `sync.Mutex`, making concurrent calls to `SetCopyright`, `SetCaption`, `SetKeywords`, and similar methods safe. The concurrency contract is documented in `doc.go`.
- **`Write` defensive raw-slice copy** (#139): `Write` now copies the raw EXIF, IPTC, and XMP byte slices from the source `*Metadata` before passing them to the format writer, preventing a caller that holds a reference to the original slices from observing in-flight writes.
- **IPTC auto-create for TIFF-based RAW** (#110): calling `Write` on a TIFF-based RAW file (NEF, ARW, DNG, ORF, RW2) now correctly auto-creates an IPTC block when none is present in the source, matching the behaviour already provided for JPEG and PNG.
- **`canCarryIPTC` and `Read` documentation corrected** (#178): the exported `canCarryIPTC` function and the `Read` doc comment now accurately describe which formats carry IPTC in an APP13/Photoshop IRB and which embed it directly in a TIFF IFD.
- **EXIF encode nil-IFD0 and nil-ByteOrder safety** (#58/#59): `exif.Encode` now returns a typed error instead of panicking when called with a nil IFD0 or a nil ByteOrder. These cases arise when `Write` is called on a `*Metadata` that was constructed programmatically rather than parsed from a file.
- **JPEG orphaned pooled buffer on segment resize** (#77): the JPEG writer no longer leaks the segment buffer back to the pool before the new-segment slice is written, closing a use-after-pool-return path.
- **`iptc.SetKeywords` UTF-8 flag** (#63): `SetKeywords` now sets the IPTC `CodedCharacterSet` (Dataset 1:90) flag to UTF-8 when any keyword contains non-ASCII characters, preventing downstream consumers from misinterpreting the encoding.
- **IPTC dataset count alloc bomb** (#71): `iptc.Parse` now caps the maximum total parsed dataset count at 65 535, preventing a crafted stream with a very large dataset-count field from forcing a proportional allocation before the bounds check fires.

### Security

- **HEIF CRITICAL: `infe`/`buildInjectComponents` OOB panic closed** (#106/#133/#137/#169/#177): two independent slice-bounds-out-of-range panic paths in the HEIF parser and injector were confirmed by the fuzzer and are now closed. Both were reachable from untrusted input via `Read` or `Write` (CWE-125, CWE-787).
- **Mutex guard on `Set*` methods eliminates data race** (#128/#148/#185): concurrent calls to `Set*` methods on the same `*Metadata` could produce a fatal Go runtime map-concurrent-write or pointer-assignment race. The internal `sync.Mutex` guard closes this race (CWE-362).
- **XMP namespace-URI and local-name injection closed** (#112/#113): the XMP encoder now applies XML attribute-value escaping to namespace URIs and validates local names against the XML NCName production before serialising. A crafted XMP file with a `"` in a namespace URI or `<` in a local name could inject arbitrary XML into the encoded output (CWE-91).
- **`io.ReadAll` OOM guard across TIFF/HEIF/RAW** (#140): format-appropriate `io.LimitReader` caps prevent a streaming or adversarially crafted file from exhausting heap memory during read (CWE-400).
- **XMP C0 control character filtering** (#170/#171): the XMP encoder now strips Unicode C0 control characters (U+0001–U+001F, excluding TAB, LF, CR) from property values and namespace URIs before serialisation. XML 1.0 prohibits these characters; their presence in encoded output would produce invalid XML (CWE-91).
- **CR3 box-walker recursion cap** (#175/#191): the CR3 box walker is now depth-capped at 64 levels, preventing stack exhaustion from pathologically nested ISO BMFF input (CWE-674).
- **PNG oversized XMP chunk guard** (#147/#181): the PNG writer now rejects payloads that would exceed the 2 GiB PNG chunk size limit before writing, preventing a 32-bit length overflow that would produce a corrupt file (CWE-190).
- **JPEG IRB Pascal-name bounds** (#151/#174): the IRB parser clamps the Pascal-name length to the remaining buffer, closing a read-past-end path reachable from a malformed APP13 segment (CWE-125).
- **TIFF integer overflow in image-start arithmetic** (#115/#172/#176/#183/#184): `uint32` arithmetic in the relocation path is now promoted to `uint64` before comparison, preventing silent overflow when image blocks are positioned near the 4 GiB boundary (CWE-190).

## [1.1.0] - 2026-06-03

### Added

- **`tiff.ErrUnsupportedMagic`**: new exported sentinel error returned when the TIFF parser encounters a BigTIFF magic number (`0x002B`). Previously the library silently misidentified BigTIFF files as ordinary TIFF; now callers can detect and handle this case explicitly with `errors.Is(err, tiff.ErrUnsupportedMagic)`.
- **`xmp.ErrDocumentTooLarge`**: new exported sentinel error returned when an XMP document exceeds the `maxXMPDocumentBytes` input cap (16 MiB, compile-time constant). Callers can use `errors.Is` to distinguish this condition from malformed-XML errors.
- **`FuzzRead`**: end-to-end fuzz target at the top-level package (`FuzzRead`) that drives the full `Read` orchestrator with arbitrary input. This joins 26 existing fuzz targets for a total of 27.
- **CI fuzz job**: a new `fuzz` CI job runs 6 fuzz targets for 10 seconds each under `-race`, catching regressions on every pull request.
- **FormatCapability knowledge-graph matrix**: the format capability matrix (which combinations of format and operation are supported) is now recorded in the project knowledge graph (the `FormatCapability` matrix mirroring `format.SupportsWrite`).

### Changed

- **JPEG ExtendedXMP GUID cap**: the JPEG parser now caps the number of distinct ExtendedXMP GUIDs at 4 per file during reassembly of multi-segment ExtendedXMP payloads (each GUID is itself capped at 16 MiB, giving a 64 MiB aggregate ceiling). Excess GUIDs beyond the fourth are dropped and the reassembled payload is marked truncated, preventing memory exhaustion from crafted multi-segment JPEGs without aborting the parse.
- **Write-support documentation corrected**: README, CHANGELOG, SECURITY.md, and `doc.go` now precisely state that `Write` is supported for JPEG, PNG, WebP, HEIF/AVIF, and Canon CR3. TIFF-based containers (TIFF, CR2, NEF, ARW, DNG, ORF, RW2) are read-only; `Write` returns `ErrWriteNotSupported` for those formats.
- **`go.mod`**: `golang.org/x/text` reclassified as a direct dependency (the `// indirect` annotation removed by `go mod tidy`).
- **Test coverage**: +207 tests added since v1.0.4. New tests cover EXIF/TIFF adversarial fuzz seeds, the `internal/iobuf` buffer pool (race, contamination, and DoS scenarios), and the top-level read orchestrator.

### Fixed

- **`iptc.Encode` receiver mutation** (`iptc/iptc.go`): `Encode` previously appended the IPTC 1:90 UTF-8 `CodedCharacterSet` marker directly to the receiver's `Records[0]` slice when emitting non-ASCII content, mutating shared state and creating a data race under concurrent `Write` calls. The fix emits the 1:90 declaration to the encoded output only (via the existing `needsUTF8Declaration` path); the receiver is now pure and idempotent.
- **`internal/iobuf` pool hardening** (`internal/iobuf/iobuf.go`): `Get(n)` now clamps negative `n` to zero instead of passing it to `make`, which would have panicked. `Put` now discards buffers whose capacity exceeds the large-tier canonical cap (`largeSize = 65536`) rather than returning them, preventing unbounded pool growth from adversarially crafted payloads.
- **DoS caps and write determinism** (`exif`, `iptc`, `xmp`, `format/jpeg`): follow-up fixes from the Sprint 8 re-audit — additional byte-count caps on IFD entry aggregation, IPTC dataset aggregation, and XMP attribute accumulation; deterministic output ordering for EXIF and IPTC write paths.
- **Untrusted-input crash sites** (`exif`, `iptc`, `xmp`, `format/*`): elimination of the remaining nil-dereference and out-of-bounds-slice-index paths reachable from attacker-controlled binary data identified in the Sprint 8 audit.

### Security

- **XMP document-level input cap** (`xmp/`): introduced `maxXMPDocumentBytes` (16 MiB, compile-time constant) as a hard ceiling on the total UTF-8 bytes accepted by a single XMP parse (checked post-normalisation, before the RDF scan). Exceeding the cap returns `xmp.ErrDocumentTooLarge` without allocating further memory, preventing memory-exhaustion attacks from crafted XMP payloads (CWE-400).
- **TIFF/BigTIFF discrimination** (`format/tiff/`): the TIFF parser now reads the magic word and immediately returns `tiff.ErrUnsupportedMagic` for BigTIFF (`0x002B`). Previously the parser would misinterpret BigTIFF offsets as TIFF-6 offsets and could seek to arbitrary positions in the file or allocate large intermediate buffers (CWE-125, CWE-400).
- **JPEG ExtendedXMP GUID cap** (`format/jpeg/`): the parser caps distinct ExtendedXMP GUIDs at 4 per file (each GUID itself capped at 16 MiB, giving a 64 MiB aggregate ceiling); excess GUIDs are dropped and the result marked truncated, preventing memory exhaustion from crafted multi-segment JPEGs (CWE-400).
- **`iptc.Encode` data race eliminated** (`iptc/`): the receiver-mutation bug described under Fixed was also a data-race vulnerability under concurrent use; the fix eliminates the race without API change (CWE-362).
- **`internal/iobuf` pool hardening** (`internal/iobuf/`): the `Get(n<0)` panic path and the oversized-buffer pool-retention path are both closed, removing two crash/memory-exhaustion vectors reachable from attacker-controlled input sizes (CWE-400, CWE-476).

## [1.0.2] - 2026-04-07

### Performance

- **XMP GPS parse**: `strings.Split` replaced with `strings.Cut`; GPS coordinate parsing is now zero-allocation (`BenchmarkGPSParse`: 0 B/op, 0 allocs/op).
- **XMP `Keywords`**: single-pass `strings.IndexByte` scan with `strings.Count`-pre-sized result slice replaces `strings.Split`; eliminates the intermediate `[]string` allocation per call.
- **XMP `AddKeyword`**: `strings.Builder` with pre-grown capacity replaces string concatenation; one allocation instead of two per keyword append.
- **XMP `SetGPS`**: `strconv.AppendFloat` into a `[32]byte` stack buffer replaces `fmt.Sprintf`; eliminates heap allocation and `fmt` reflection overhead per GPS encode.
- **XMP `writeMultiValuedProperty`**: `strings.IndexByte` loop replaces `strings.Split`; the `[]string` allocation on every multi-valued property encode is eliminated.
- **XMP packet scanner**: `[]byte("?>")` literals extracted to package-level variables; no heap allocation on every `Scan` call.
- **XMP RDF parser**: per-call `[]byte("-->")` and `[]byte("?>")` literals extracted to package-level; `rdf:Alt` item concatenation uses a pooled `strings.Builder`; named-entity comparison uses `switch string(ref)` (compiler-optimised zero-alloc path).
- **IPTC ISO-8859-1 decoder**: per-call `charmap.ISO8859_1.NewDecoder()` replaced with a `sync.Pool`; decoder is `Reset()` before each use.
- **HEIF write path**: `buildIlocBox` and `buildMetaBox` now measure required length in a first pass and allocate a single pre-sized output buffer, eliminating incremental `append` reallocs; `appendUintN` uses `binary.BigEndian.AppendUint16/32/64` instead of `make([]byte, n)` per field.
- **JPEG segment copy**: all four `append([]byte(nil), ...)` call sites replaced with `bytes.Clone`.
- **PNG write path**: `crc32.NewIEEE()` pooled via `sync.Pool` to avoid per-chunk hash allocation; 8-byte chunk header stack-allocated (`[8]byte` instead of `make([]byte, 8)`).
- **PNG read path**: `readChunk` refactored to a callback pattern; the pooled buffer is passed directly to the callback without cloning in the common (non-retained) path, saving one allocation and one copy per pass-through chunk.
- **WebP write path**: `bytes.Buffer` in `buildWebPBody` pooled via `sync.Pool`; 4-byte RIFF chunk size field stack-allocated.
- **ORF/RW2 write path**: only the 4-byte magic header is patched in-place on the `io.ReadAll`-owned slice; the previous full-file copy is eliminated.
- **EXIF `filterEntries`**: accepts an `extraCap` argument to pre-size the result slice, avoiding a realloc when `buildIFD0Entries` appends trailing entries.
- **`internal/bmff`**: `Box.Equal([4]byte) bool` added for zero-alloc box type comparison.
- **`internal/riff`**: `Chunk.Equal([4]byte) bool` added for zero-alloc FourCC comparison.
- **XMP date layouts**: inline `[]string` literal in `metadata.DateTime()` hoisted to a package-level `[3]string` array, eliminating the per-call slice header allocation.

### Changed

- All packages now define package-level sentinel error variables (`ErrXxx`) for every error previously constructed inline with `errors.New` or `fmt.Errorf`; callers can now use `errors.Is` for reliable error identity checks. Affected packages: `exif`, `format/heif`, `format/jpeg`, `format/png`, `format/tiff`, `format/webp`, `format/raw/cr3`, `format/raw/orf`, `format/raw/rw2`, `xmp`, and the top-level package.
- Import ordering enforced across all files (`gci` linter, stdlib → external → internal grouping).
- `t.Parallel()` added to all table-driven tests and `t.Run` callbacks across all 43 test files; the entire test suite now runs with maximum parallelism under `go test -race ./...`.
- Linter suite expanded by five additional rules: `err113` (no inline error construction), `godot` (comment punctuation), `nestif` (nesting depth ≤ 4), `godox` (no TODO/FIXME/HACK comments), `gci` (import ordering), `paralleltest`/`tparallel` (parallel test enforcement), and `funlen` (function length ≤ 80 lines / 60 statements).
- `metadata.DateTime()` refactored from four levels of nesting to guard clauses (cyclomatic complexity reduced from 6 to 1; behaviour unchanged).

### Fixed

- **`sync.Pool` use-after-put race in `format/detect.go`**: `mapMakeToFormat` was called after `tiffScanPool.Put(buf)` despite `makeRaw` being a subslice of the pooled buffer; reordered to call `mapMakeToFormat` before `Put`.
- **`sync.Pool` use-after-put race in `format/heif/heif.go`**: `extractFromMetaData` was called after `iobuf.Put(hdrPtr)` despite `metaData` being a subslice of the pooled buffer; reordered likewise.
- **PNG data lifetime bug**: `eXIf`, `tEXt`, and `iTXt` chunk handlers in `readChunk` were retaining references to a pooled buffer slice without cloning; the callback-pattern refactor ensures retained data is always copied from the pool before the buffer is returned.

## [1.0.0] - 2026-04-04

### Added

- **Unified read/write API**: `Read(r io.ReadSeeker) (*Metadata, error)` and `Write(r io.ReadSeeker, md *Metadata) ([]byte, error)` — the container format is detected automatically from magic bytes; no configuration required.
- **`Metadata` struct** with typed accessor and setter methods for all common fields: camera make and model, lens, capture date/time, GPS coordinates (decoded to decimal degrees), copyright, artist, caption/description, keywords, rating, orientation, exposure, focal length, ISO, aperture, and shutter speed.
- **EXIF parser and writer**: full IFD traversal (IFD0, IFD1, SubIFD, GPS IFD, Interop IFD), tag registry covering approximately 200 standard CIPA DC-008/JEITA CP-3451 tags, both big-endian and little-endian byte order, and all TIFF 6.0 data types.
- **MakerNote dispatch** for 11 manufacturers — Canon, DJI, Fujifilm, Leica, Nikon, Olympus, Panasonic, Pentax, Samsung, Sigma, and Sony — each with a brand-specific tag registry.
- **IPTC IIM parser and writer**: all standard records (Records 1–9), dataset decoding, APP13/Photoshop IRB extraction, and UTF-8 character encoding via the IPTC envelope (Dataset 1:90).
- **XMP parser and writer**: full RDF/XML parsing, all RDF collection types (`rdf:Seq`, `rdf:Bag`, `rdf:Alt`), packet scanning and in-place injection, and a namespace registry covering all standard schemas (`dc`, `xmp`, `xmpRights`, `photoshop`, `Iptc4xmpCore`, `Iptc4xmpExt`, `exif`, `tiff`, `aux`, `GPS`).
- **Container support** — read for all formats: JPEG (APP1/APP13 segments), TIFF, PNG (`iTXt`/`tEXt` chunks), WebP (RIFF VP8X/EXIF/XMP chunks), HEIF/HEIC (ISO BMFF box traversal), and the RAW variants Canon CR2, Canon CR3, Nikon NEF, Sony ARW, Adobe DNG, Olympus ORF, and Panasonic RW2. Metadata write (injection) is supported for JPEG, PNG, WebP, HEIF/AVIF, and Canon CR3; TIFF-based containers (TIFF, CR2, NEF, ARW, DNG, ORF, RW2) are read-only in this release (`Write` returns `ErrWriteNotSupported`).
- Format detection by magic bytes — never by file extension.
- GPS decimal-degree decoding and encoding: degrees/minutes/seconds rational values are decoded to `float64` and re-encoded on write.
- Convenience CLI example programs shipped under `examples/`: `read-metadata`, `write-metadata`, and `batch-keywords`.
- Zero-allocation parsing fast path across all format parsers: `sync.Pool` for reusable buffers, `[]byte` slice references over copies, and lazy field parsing — only fields the caller accesses are decoded.

### Fixed

- Panic-free handling of malformed, truncated, and corrupted image files across all parsers.
- Integer overflow protection in HEIF box-length arithmetic and TIFF IFD entry counts.
- IPTC IIM record boundary compliance (IPTC IIM 4.2, §2).
- HEIF/HEIC container rewritten for correct nested-box traversal (ISO 14496-12).
- WebP RIFF chunk four-byte alignment padding applied correctly on write.
- RAW format IFD pointer resolution for manufacturer-specific sub-IFDs.

### Security

- All parsers harden against attacker-controlled offsets, lengths, and counts in binary data; no out-of-bounds read is possible on any `io.ReadSeeker` consumer.
- Fuzz targets `FuzzParseEXIF`, `FuzzParseIPTC`, and `FuzzParseXMP` ship as part of the test suite so regressions are caught automatically.
